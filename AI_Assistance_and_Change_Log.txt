--------------------------------------------------------------------------------
2.1  server.py
--------------------------------------------------------------------------------
(a) Updated one import line to also pull in `is_connected` from
    reliability.py (needed for (g) below). This is the one line that
    touches a pre-existing statement rather than adding a new one.

(b) Added a helper, _room_state_for_session(), that looks up the live
    state of whatever room (if any) my session is bound to.

(c) Added a helper, _effective_trivia_position(), that decides which
    trivia set index and question index a request should use. For
    self-paced sessions this is unchanged from before. For host-paced
    sessions, it instead reads the room's own live, shared question
    index, since in host-paced mode every player needs to see the same
    question at the same time -- a value cached once at join time can't
    do that once the host advances the room.

(d) Updated get_trivia() and verify_answer() to use that new helper
    instead of reading the session directly. This fixed a real bug I
    caught with automated testing: my first pass at host-paced sync only
    updated get_trivia(), so a host-paced player's submitted answer could
    have been graded against a stale, previously-seen question instead of
    the one actually on their screen.

(e) Updated next_question() to return HTTP 403 for any session in a
    host-paced room, since players in that mode shouldn't advance their
    own progress -- only the host does, through (f).

(f) Added a new route, POST /api/rooms/<room_code>/next (advance_room /
    advance_room_question), teacher-only, that advances a room's shared
    question index by one. This is what makes the "Next Question" button
    in Host-Paced mode actually synchronize every player in the room,
    instead of only advancing the host's own personal progress like it
    did before.

(g) Added a new route, GET /api/rooms/<room_code>/connectivity
    (get_room_connectivity), reporting per-player whether they've sent a
    heartbeat PING within reliability.py's timeout window. This activates
    an existing reliability.py function (is_connected()) that existed in
    that file already but was never called anywhere before -- so this
    satisfies the "Timeout Detection" reliability requirement using code
    a teammate had already written but never wired up.

(h) Updated _apply_room_to_session() to also cache a room's pacing_mode
    in the session at join/create/start time, so self-paced sessions
    don't pay for an unnecessary extra network lookup on every question
    fetch -- only host-paced sessions do that lookup, since they're the
    only ones that actually need live room data.

(i) Added two new entries to the existing error-mapping dictionary in
    _lobby_error(): "room is not active" -> 409, and "only the host can
    advance the room" -> 403.

(j) Added a runnable entry point at the bottom of the file:
        if __name__ == "__main__":
            app.run(host="0.0.0.0", port=8000)
    This lets the file run directly with `python3 server.py`, and
    critically binds to 0.0.0.0 instead of Flask's default
    127.0.0.1-only. This was necessary for the Multi-Host Communication
    requirement -- without it, no machine other than the one running
    server.py could ever reach it.

PART 3: HOW MY FRONTEND (templates/index.html, static/script.js) WORKS
================================================================================

I did not write this code -- Gemini Plus generated it and Claude later
modified/extended it, as described in Part 1. The explanation below is my
own understanding of how it works, put together so I can explain any part
of it if asked, per the course's requirement that I understand all
submitted code regardless of who/what generated it.

--------------------------------------------------------------------------------
3.1  Overall shape
--------------------------------------------------------------------------------
This is a single-page application. There's one HTML page; every "screen"
(Home, Join Room, Solo Practice, Host Setup, Live Host Scoreboard,
Dashboard, Login, Sign-up) is a <div class="view"> that exists in the
page at all times and is just hidden with CSS until it's the active one.

switchView(viewId) is the core of this: it removes "active" from every
view, adds it to the requested one, and updates the highlighted nav
button. There's no real routing or page reloads.

All behavior lives in static/script.js, loaded with one <script> tag.
There's no framework -- state is plain JavaScript variables at the top of
the file, and functions read from and write to the DOM directly.

--------------------------------------------------------------------------------
3.2  Global state
--------------------------------------------------------------------------------
A handful of "let" variables track the logged-in user (or null for a
guest), the selected avatar, score/streak, which quiz is active, whether
the current room is self-paced or host-paced, and several setInterval
handles for background polling (room standings, question polling,
heartbeat, host countdown timer). Since nothing enforces state updates
automatically, most functions that change one of these variables
immediately update the matching DOM element right after.

There's also a hardcoded quizDatabase object with three demo quizzes,
used purely as a fallback when the real backend is unreachable -- every
function that needs question data tries the real backend first.

--------------------------------------------------------------------------------
3.3  Talking to the backend
--------------------------------------------------------------------------------
Every backend call follows the same shape: try fetch(), use the real
response if it succeeds, fall back to local-only behavior and a toast
notification if it fails. This means the app still runs for a demo even
if the backend isn't up, though a real multiplayer session needs it.

Two routes (verify answer, analytics) are documented as GET but I send
POST -- this is intentional, and explained in comments directly above the
relevant functions: browsers cannot send a request body on GET at all,
so POST is the only option that could ever work, even though it doesn't
match what the backend currently accepts.

Signed write requests (creating a quiz, verifying an answer) compute an
HMAC-SHA256 signature client-side using the Web Crypto API, using a
shared secret near the top of the file that has to match the
TRIVIA_HMAC_SECRET environment variable the backend was started with.

--------------------------------------------------------------------------------
3.4  Major feature areas
--------------------------------------------------------------------------------
Auth: handleAuthSubmit() is shared by Login and Sign-Up; it checks which
view is active to know which one it's handling.

Home / search: filterQuizzes() does a simple substring match as I type.

Quiz builder: addQuestionToBuilder() adds a blank question card;
updateAnswerFields() swaps the answer UI to match the selected question
type; handleSaveBuilderQuiz() reads every card into the JSON shape the
backend expects and remembers the returned trivia-set index so that quiz
can later be hosted as a real live room.

Solo Practice: fully local/offline by design -- never touches the
network. Grading uses checkAnswerAgainstQuestion(), which requires an
exact set match for "Multiple Select" questions, matching the backend's
real grading rule.

Multiplayer -- joining: handleJoinGame() posts to /api/rooms/join, stores
the room's pacing_mode, and starts the heartbeat loop.

Multiplayer -- Self-Paced: I answer, the backend advances my own
progress, loadMultiplayerQuestion() fetches the next question.

Multiplayer -- Host-Paced: I don't advance my own progress after
answering (the backend rejects that); instead
startStudentQuestionPolling() polls every 2 seconds and updates the
displayed question once it detects the host dispatched a new one. On the
host side, dispatchNextHostQuestion() calls the real advance endpoint.

Host scoreboard: pollRoomStandings() polls both the roster and the
connectivity endpoint every 3 seconds and renders a live table with a
green/red online-offline indicator per player.

Reconnect: attemptReconnect(), called once on page load, silently checks
whether this session was mid-game; if so it restores me straight into the
gameplay view, otherwise it does nothing.

--------------------------------------------------------------------------------
3.5  Things I should be ready to explain
--------------------------------------------------------------------------------
- Why the search bar, avatar picker, and Solo Practice work with no
  backend involvement: they're legitimately client-side features, not
  incomplete integrations.
- Why Self-Paced and Host-Paced use two different sync strategies: a
  deliberate response to the backend tracking one shared question index
  per room, which only matters when the host needs to control pacing for
  everyone.
- Why I used a 2-second poll instead of an instant push for Host-Paced
  sync: this stack has no WebSocket/push mechanism, so polling was the
  only option; 2 seconds balances responsiveness against request volume.
  This is a legitimate point for my "Design Challenges" or "Lessons
  Learned" section.
